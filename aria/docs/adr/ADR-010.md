# ADR-010: Module Isolation Boundary Rules

**Status**: Accepted
**Date**: 2026-05-16
**Decided by**: Sam_Architect + Claude gate review

## Context

Aria has 6 product modules. Without explicit boundary rules, modules will accumulate cross-dependencies over time — leading to a "big ball of mud" where changing one module breaks another unexpectedly. This is especially dangerous with 9 agents building in parallel.

## Decision

**Rule 1: No cross-module imports.**
`aria.modules.flashcards` must never import from `aria.modules.conversation` or any other module. Cross-module communication happens only through:
- Shared core layer (`aria.core.*`) — config, constants, exceptions, logging
- Shared Pydantic schemas in `aria.modules.<source>.schemas` exposed as read-only (no import of service or model classes)
- Events/messages via Redis pub/sub (Phase 4+)

**Rule 2: Each module owns its full vertical slice.**
Router → Service → Models → Schemas. No shared SQLAlchemy models between modules. Foreign keys between module tables are allowed in the database but not in Python ORM imports — use raw IDs and look up as needed.

**Rule 3: The services layer is shared, not modules.**
`aria.services.*` (STT, LLM, TTS, etc.) is a shared infrastructure layer, not a module. All modules may import from `aria.services.factory` via `Depends()`.

**Enforcement**: Quinn_QA runs at every gate:
```bash
grep -r "from aria.modules" aria/backend/modules/ | grep -v "__init__" | grep -v "\.schemas"
```
Any cross-module import that is not a schema import fails the gate.

## Consequences

**Positive**:
- Any module can be extracted to a separate microservice in the future with minimal refactoring
- Bugs in one module cannot cause cascade failures in another
- Agents can work on different modules in parallel without merge conflicts

**Negative/Risk**:
- Some data duplication (e.g., session_id stored in both conversation and flashcard tables)
- Can feel restrictive when a shortcut cross-import would save 10 lines

**Mitigated by**: The core layer provides all shared utilities. The event bus (Redis pub/sub) handles cross-module notifications (e.g., "session ended → generate flashcards") without direct imports.

## Alternatives Rejected

| Alternative | Why rejected |
|---|---|
| Monolithic shared models | High coupling; all 9 agents would conflict on the same models file |
| Microservices from day 1 | Over-engineered for MVP; network overhead adds latency to analysis pipeline |
| No explicit rules | Guaranteed to become a big ball of mud by Phase 5 |
